# 経営者リサーチツール 要件定義書

作成日: 2026-08-29 / 更新日: 2026-08-30 / バージョン: 0.3（Phase 0 パイロット完了を反映）

---

## 1. 目的

TikTokで発信している経営者のアカウントURLを入力するだけで、その人の全発信を収集・構造化し、**自分の事業に転用できる形**でレポート化する自分専用ツール。

ゴールは「要約を読むこと」ではなく、**この事業モデルを日本で再現できるか判断すること**。

## 2. スコープ

### 対象
- TikTok（Phase 1）
- **日本語・英語アカウントの両方**（英語圏は国内に事例がないモデルを拾うのが目的）
- 自分1人が使うローカル/個人環境で動くツール
- 経営者・事業者アカウントのリサーチ

### スコープ外（現時点）
- YouTube / X 対応（Phase 3で検討）
- **動画内の画面テキストのOCR取得**（音声とキャプションのみを対象とする）
- 他ユーザーへの公開、認証、課金
- リアルタイム監視・新着自動追跡
- 動画そのものの保存・再配布

## 3. 想定利用フロー

1. 気になる経営者のTikTokプロフィールURLをコピー
2. ツールに貼り付けて収集ジョブを開始
3. 数分〜数十分後に完了通知
4. 1枚レポートを読み、判断する
5. 気になる点はチャットで深掘り質問する

## 4. システム構成

```
[収集バッチ / Python]
  TikTok収集 → 音声抽出 → 文字起こし → LLM抽出 → DB保存
                                                    ↓
[閲覧UI / Next.js] ← レポート表示・チャット ← ← ← ← ←
```

収集と閲覧を分離する。収集は失敗・再実行が前提の重い処理なので、UIから同期実行しない。

## 5. 機能要件

| ID | 機能 | 内容 | 優先度 |
|---|---|---|---|
| F-01 | アカウント登録 | プロフィールURLを入力し収集ジョブを作成 | 必須 |
| F-02 | 動画メタ収集 | 動画URL・キャプション・投稿日・再生数・いいね数を取得 | 必須 |
| F-03 | 音声取得 | 対象動画の音声をダウンロード | 必須 |
| F-04 | 文字起こし | Geminiで文字起こし。**原語のまま保存**（翻訳しない） | 必須 |
| F-05 | 動画単位抽出 | 固定スキーマでJSON抽出（§7）。**出力は常に日本語** | 必須 |
| F-06 | アカウント統合レポート | 全動画の抽出結果を1枚に統合 | 必須 |
| F-07 | チャット | 全文起こしを文脈に入れて質問応答 | 必須 |
| F-08 | ジョブ管理 | 進捗表示・失敗時の部分再実行 | 必須 |
| F-09 | 手動メモ | レポートに自分の所感を追記 | 推奨 |
| F-10 | 横断比較 | 複数アカウントを項目軸で並べる | 後回し |
| F-11 | 再収集 | 差分のみ追加取得 | 後回し |

## 6. データモデル

```
accounts
  id, platform, handle, profile_url, display_name,
  follower_count, bio, collected_at, status

videos
  id, account_id, video_url, caption, posted_at,
  view_count, like_count, duration_sec

transcripts
  id, video_id, text, language, model, cost_yen

extractions
  id, video_id, payload(JSON = §7スキーマ), model, created_at

reports
  id, account_id, markdown, generated_at, model, user_note
```

## 7. 抽出スキーマ（本ツールの核）

動画1本ごとにこの型で抽出する。項目を固定しないと粒度がバラつき、比較不能になる。

```json
{
  "has_business_content": true,
  "source_language": "en",
  "topic": "この動画で語られている主題",
  "business": {
    "what": "何を売っているか",
    "who": "誰に売っているか",
    "how_much": "単価・価格帯",
    "revenue_model": "収益の発生構造"
  },
  "numbers": [
    { "label": "月商", "value": "300万円", "is_verifiable": false }
  ],
  "origin": {
    "motivation": "なぜ始めたか",
    "initial_cost": "初期投資",
    "time_to_revenue": "収益化までの期間",
    "prior_skill": "前提スキル・人脈"
  },
  "requirements": ["再現に必要なリソース"],
  "failures": ["失敗談・つまずき"],
  "claim_vs_fact": {
    "claims": ["本人の主張（未検証）"],
    "facts": ["検証可能な事実"]
  },
  "japan_applicability": {
    "score": 1,
    "reason": "日本で再現できるか、法規制・商習慣の壁",
    "existing_jp_competitors": ["国内で既にやっている事業者"]
  },
  "confidence": 0.8
}
```

### 重要な設計判断

- **翻訳ステップは作らない**: 文字起こしは英語なら英語のまま保存し、抽出時にLLMが直接日本語で出力する。「英訳→和訳」の二段階にすると情報が劣化し、コストも倍になる。チャットも英語原文のまま文脈に入れて日本語で答えさせる。
- **`claim_vs_fact` の分離**: TikTokの経営者系は数字を盛る傾向がある。本人の主張と検証可能な事実を分けないと、レポートが誇張の集合体になる。
- **`japan_applicability`**: 単なる要約ツールと差がつくのはここ。英語圏アカウントではこの項目が本体になる。国内に事例がないモデルほど価値が高い一方、法規制・決済・商習慣の壁で再現不能なことも多いため、必ず理由まで書かせる。
- **`has_business_content`**: 日常動画やネタ動画を除外するフラグ。これがないと統合レポートがノイズだらけになる。

## 8. レポート出力構成（1人1枚）

1. 基本情報（アカウント / フォロワー / 発信期間 / 分析本数）
2. 事業サマリー（3行）
3. 収益モデル図解（誰が誰に何を売って何円か）
4. 語られた数字一覧（主張 / 事実を明示）
5. 立ち上げ経緯とタイムライン
6. 必要リソース・前提スキル
7. 失敗談・語られたリスク
8. **日本での再現性評価**（可否 / 障壁 / 国内競合 / 参入余地）
9. 自分の所感メモ欄

## 9. チャット仕様

- 全文起こし（100本で数十万字程度）を**そのままコンテキストに投入**する
- ベクタDB / RAGは組まない。この規模では精度が落ちるだけで、実装コストに見合わない
- アカウント単位でチャットセッションを持つ
- 将来的に文字数がコンテキスト上限を超えた場合のみRAGを検討

## 10. 非機能要件

| 項目 | 要件 |
|---|---|
| 処理本数 | 1アカウントあたり**直近100本**を上限とする（投稿日の新しい順） |
| 処理時間 | 100本で30分以内（バックグラウンド実行） |
| コスト | 1アカウントあたり1,000円以内 |
| 同時実行 | 1ジョブずつで可。並列不要 |
| 失敗時 | 動画単位でリトライ可能。全体やり直しにしない |
| データ保管 | 文字起こしは保存、音声ファイルは処理後に削除 |
| 冪等性 | 同じ動画を二重に文字起こししない（コスト直結） |

## 11. 技術スタック

- 収集: Python + **RapidAPI tiktok-scraper7**（vad-dashboard の `lib/tiktok.ts` をPython移植。既存の `RAPIDAPI_KEY` を流用）
- 文字起こし: **Gemini**（vad-dashboard の `GOOGLE_API_KEY` を流用。動画DL→ffmpegで音声抽出→Gemini）
- 抽出・要約・チャット: Claude API（`claude-opus-4-8`、構造化出力でスキーマ保証）
- DB: Supabase（Phase 2から。Phase 0-1はローカルJSON/Markdown）
- UI: Next.js + Tailwind + shadcn/ui
- 実行: ローカル or 自前サーバー上のバッチ

実装済みスクリプト: `collector/collect.py`（F-01,02）/ `collector/transcribe.py`（F-03,04）/ `collector/extract.py`（F-05）/ `collector/report.py`（F-06）

## 12. コスト実測（Phase 0 パイロット5本の実績から100本換算）

| 項目 | 実測ベース概算 |
|---|---|
| 動画メタ収集（RapidAPI） | 既存契約枠内。約4リクエスト/アカウント |
| 文字起こし（Gemini） | 数十円/100本 |
| 動画単位抽出（Claude Opus 4.8） | 約600円/100本（実測: 5本で約30円） |
| 統合レポート生成 | 約50〜100円（実測: 5本分で約22円。100本分は入力が増える） |
| **合計** | **約700〜800円/アカウント**（上限1,000円以内に収まる） |

## 13. リスク・制約

| リスク | 内容 | 対応 |
|---|---|---|
| 規約 | 他人アカウントの機械的収集はTikTok規約上グレー | 自分のリサーチ用途に限定。公開しない |
| 取得失敗 | TikTok側の仕様変更でスクレイパーが壊れる | 収集層を差し替え可能な形で疎結合にする |
| URL失効 | `play_url`（動画DL用URL）は署名付きで短命 | メタ収集後は速やかに文字起こしまで実行する。失効時はメタ再収集 |
| 情報の信頼性 | 誇張・演出された数字 | `claim_vs_fact` で分離 |
| 音声品質 | BGM過多・字幕のみの動画は文字起こし不可 | キャプションで補完し、`confidence` を下げる |
| 同音異義語 | 文字起こしの誤変換（実例: 小売業→氷業） | プロンプトでビジネス文脈を明示。レポートの業種名等に違和感があればユーザーが校正し、データまで遡って置換する |
| コスト暴走 | 大量アカウントの一括投入 | 1回あたりの処理本数に上限を設ける |
